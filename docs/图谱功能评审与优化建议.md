# 图谱功能评审与优化建议

> 评审范围：career-agent 项目的"职业路径图谱（Career Path Graph）"端到端实现
> 评审视角：架构合理性 / 数据模型 / Neo4j 查询与持久化 / 图谱构建算法 / Agent 推理 / 前端可视化 / 测试与可观测性 / 安全与多租户
> 评审产出：现状结论 + 优先级化的优化建议清单

---

## 一、模块全景

### 1.1 后端

当前同时存在**两套并行的图谱实现**：

| 维度 | V1（`modules/career-path/`） | V2（`modules/jobs-intelligence/`） |
| --- | --- | --- |
| 路由前缀 | `/api/v1/career-paths` | `/api/v2/career-paths` |
| 节点来源 | 硬编码 12 个 `CANONICAL_CAREER_ROLES` + 25 条边的 seed | 自动从 `v2_manual_job_portraits` 推断 / Pi Agent 生成 |
| Cypher 标签 | `:CareerRole` + `:CAREER_PATH` | `:CareerRoleV2` + `:CAREER_PATH_V2` |
| 关系类型 | promotion / transition | promotion / transition / skill_migration |
| 路径推荐 | service 内 DFS + transition_cost 惩罚 | service 内只取 1~2 hop 直接拼路径 |
| 是否对外暴露 | 是（matching、report 仍依赖） | 是（前端 `CareerPathPage` 默认调用） |

**关键事实**：`apps/backend/src/app.ts` 同时挂载 V1 和 V2，且 V1 service 还被注入到 `matchingService` 和 `reportService`，所以不是简单"V2 替代 V1"的关系，而是两套都在线上跑。

### 1.2 图谱生成的三种模式

`jobs-intelligence` 模块下并存了 **三个生成器**，调用关系互斥但代码各自独立：

1. `jobs-intelligence.graph.ts` 的 `buildAutoCareerGraph(profiles, jobTitleById)`：基于 `JobProfileV2Record`（旧 v2 画像），用倒排索引 + Jaccard 召回（被 `jobs-intelligence.graph.test.ts` 单测覆盖，但**实际未在 service 中调用**）。
2. `jobs-intelligence.graph.manual.ts` 的 `buildCareerGraphFromManualPortraits`：基于 `v2_manual_job_portraits` 表，O(n²) 全量比对 + 候选剪枝 + 兜底补边（service 默认走这条）。
3. `jobs-intelligence.graph.agent.ts` 的 `generateCareerGraphByAgent`：把岗位画像简化成 8 个 token 喂给 Pi Agent，期望返回完整 JSON 图谱（120s 超时，失败降级到 2）。

### 1.3 前端

入口仅 `apps/frontend/src/features/career-path/pages/CareerPathPage.vue`（1071 行）：

- AntV G6 v5 渲染关系图（d3-force 布局）；
- ECharts 雷达图渲染 7 维岗位/学生对比；
- 路径推荐列表用模板字符串呈现，靠 `formatRouteText` 用正则把 `job-{id}` 替换为可读名称。

## 二、问题与风险（按严重程度排序）

### 2.1 架构层面（高优先级）

**问题 1：V1/V2 双轨并行，长期维护成本高**

- 节点/边/关系的 TS 类型在 contracts 里定义了两套（`CareerPathNode/CareerPathEdge` 复用，但 `CareerGraphNodeRecord/CareerGraphEdgeRecord` 又是另一套）。
- Neo4j 中存了两个独立子图（`:CareerRole` 与 `:CareerRoleV2`），既无引用一致性也没有 cross-walk。
- `buildRouteRecommendations` 在 V1 service 和 V2 service 中都各写了一份，逻辑相似但参数与产出不一致：V1 会算 `TRANSITION_COST_PENALTY` 和 `gap_skills` 惩罚，V2 直接拿 `edge.score` 平均。
- 推荐 `route.steps` 里 V2 的 `title` / `role_key` 居然写的就是节点 ID `job-123`，依赖前端正则二次替换才能展示。

**问题 2：图谱生成三套代码并行**

- `buildAutoCareerGraph`（`graph.ts`）写完后没有进入主链路（service 只引用了 manual 和 agent），单测还在维护，纯死代码。
- `manual` 和 `agent` 的输出 schema 一致，但 `manual` 用了 `stableJobIdFromName` 生成虚拟 job_id（SHA1 截 8 位 hex 取模），`agent` 直接用 portraits 传入的 job_id。两者落库后混在 `:CareerRoleV2` 表里，主键空间存在碰撞风险。

**问题 3：前端把"图谱兜底岗位"硬编码**

```ts
const PREBUILT_GRAPH_JOB_IDS = [1730415757, 1683349906, 1193271204, 1731015984, 1410409555];
```

后端 404 时前端自动回退到这 5 个 ID 之一展示。这是把生产环境的兜底策略下沉到 UI 层，会让任意一次图谱重建之后这 5 个 ID 失效，且测试环境很难复现。

---

### 2.2 数据模型（高优先级）

**问题 4：节点 ID 用字符串拼接 `job-{job_id}`**

- 字符串 ID 的代价是必须靠正则 `/job-\d+/g` 还原可读名称，`formatRouteText` 把这个责任交给前端。
- `manual` 流程下 `job-${stableJobIdFromName(...)}` 与真实 jobs 表 ID 没有强关联，路径页跳到匹配/报告时会断链。
- DTO 里 `step.title === step.role_key === edge.source` 都是 `job-123` 这种内部 ID，等于把"展示名"和"内部 ID"绑死了。

**问题 5：family、level 没有统一约束**

- V1 用 `family: "engineering" | "data-ai" | ...`（自定义枚举），V2 用 `normalizeFamily` 把 `category` 直接小写化作 family。
- V1 `level` 取值 `1~3`，V2 `level` 取值 `1~5`（`clampLevel`），且 V2 还混入了"加权 7 维分数取整"的算法。两套统计不可对比。
- 所有 string 字段没有索引/CHECK，跨族迁移的判定很容易被脏数据破坏。

**问题 6：route_id 易碰撞**

`route_id = pathEdges.map(e => e.id).join("__")`，两条不同次序的同源同终边可能拼出相同 id；前端 `:key=route_id` 时会导致渲染错乱。

---

### 2.3 Neo4j 查询与持久化（高优先级）

**问题 7：`syncGraph` 在 V2 里用了"DETACH DELETE 全表 + UNWIND 重建"**

```cypher
MATCH (node:CareerRoleV2) DETACH DELETE node
```

- 没有事务包裹，删完到写完之间任何并发查询都会拿到空图（前端会跳到兜底 ID）。
- 10K+ 节点级别会引起明显抖动，且 generated_at 不是真正的快照版本，无法回滚。

**问题 8：`getSubgraph` 直接把 depth 拼进 Cypher 字符串**

```ts
MATCH path = (target)-[:CAREER_PATH_V2*0..${normalizedDepth}]-(related:CareerRoleV2)
```

虽然有 `clamp(1,3)` 保护，但这是反模式——一旦 depth 校验被绕过即变成注入面。Neo4j 推荐用参数 + APOC `apoc.path.expandConfig` 处理变长路径。

**问题 9：约束/索引仅有 `id UNIQUE`**

- 没有 `family`、`level`、`job_id` 上的 lookup index，会让基于过滤的查询走全表扫描。
- `relation_type`、`score` 在过滤时（V2 service 的 `filter(... edge.score >= query.min_score)`）也是先全部捞回内存再过滤，本应在 Cypher 里 `WHERE rel.score >= $minScore`。

**问题 10：driver 配置/超时缺失**

`createNeo4jDriver` 只调了 `neo4j.driver(uri, auth.basic(...))`，没有设置：

- `connectionAcquisitionTimeout`
- `maxConnectionPoolSize`
- `connectionTimeout`
- `disableLosslessIntegers` 或显式 `toNeo4jNumber` 转换（已部分有，但散落各处）

线上一旦 Neo4j 抖动，会直接吃掉请求队列。

**问题 11：错误识别用正则**

```ts
return /ServiceUnavailable|SessionExpired|ECONNREFUSED|ENOTFOUND|Connection|network/i.test(...)
```

`neo4j-driver` 已经有 `Neo4jError.code`（`Neo.TransientError.*`、`Neo.ClientError.Security.Unauthorized` 等）以及导出的 `error` 字符串常量，应优先用 code 判断。

### 2.4 图谱构建算法（高优先级）

**问题 12：相似度只看技能 Jaccard，缺乏权重**

- 所有技能在 `professional_skills` 中等权处理。"Java"、"沟通"、"系统设计" 当作同等贡献，导致跨族迁移会把"沟通能力"作为关键迁移技能匹配，召回质量差。
- 阈值 `MIN_PROMOTION_JACCARD = 0.2` / `MIN_TRANSITION_JACCARD = 0.18` / `MIN_TRANSITION_OVERLAP = 2` 是 magic number，没有标注调优记录或评测基线。

**问题 13：transition_cost 完全由 `gap_skills.length` 决定**

```ts
function resolveTransitionCost(gapCount: number) {
  if (gapCount <= 2) return "low";
  if (gapCount <= 5) return "medium";
  return "high";
}
```

- 不考虑技能稀缺度（"Kubernetes" vs "Markdown"显然代价不同）。
- 不考虑技能学习曲线（编程语言 vs 业务领域）。
- 不参考任何外部信号（招聘市场需求、薪资跳变、地域）。

**问题 14：`score` 公式是"基础分 + Jaccard × 系数 + overlap × 常数"**

- promotion: `Math.round(58 + jaccard*34 + overlap*3)`
- transition: `Math.round(48 + jaccard*40 + overlap*4)`
- skill_migration: `Math.round(46 + jaccard*44 + overlap*3)`

魔数全部 inline，没有标定，最终前端把它当"建议分"展示，但**没有任何评测/校准依据**。

**问题 15：路径推荐质量低**

V2 `buildRouteRecommendations`：

```ts
const outgoing = edges.filter(... === relationType).sort(score desc).slice(0,3);
return outgoing.map(firstEdge => {
  const follow = edges.filter(... source===firstEdge.target ...).sort(score desc)[0];
  ...
})
```

- 只取 1~2 hop，没有考虑路径多样性（可能 3 条推荐都是同一族）。
- 没有去重（首边 A→B 和 B→C 与首边 A→C 的语义可能高度重合）。
- `suitability_score = pathEdges.score 平均`，没有考虑路径长度、学生现状、跨族跳跃。
- `summary` 是固定模板字符串，对所有岗位都一样：

```ts
return route_type==="promotion"
  ? "同岗位族职级递进路径，强调技能加深与复杂度提升。"
  : "跨岗位族可迁移路径，强调可复用技能与补齐差距技能。";
```

**问题 16：兜底补边逻辑不可观测**

`supplementIsolatedNodes` 与 `supplementTransitionCoverage` 写入的边在前端无法识别（reason 里写"兜底补边"，但 `score` / `relation_type` / `id` 与正常边混在一起），影响图谱评测口径。

### 2.5 Agent 模式（中高优先级）

**问题 17：单次 LLM 推理处理整张图，无法 scale**

- `GRAPH_AGENT_TIMEOUT_MS = 120_000`，岗位多于 ~60 个就会因为 token 限制截断或超时。
- 没有分批（按 family 分片 / 滚动窗口）、没有 cache（同一画像两次跑就是两次 LLM）。
- 失败后只 log warn 然后 fall back，前端无法感知 `generation_mode` 的变化（`generateCareerPathGraph` 返回 `generation_mode: "agent"` 或 `"rule"`，但 `getCareerPathGraph` 不返回，前端只看到 `graph_version` 字符串）。

**问题 18：JSON 提取不稳健**

```ts
function extractJsonObjectFromText(rawText) {
  // 1) ```json ... ``` 围栏
  // 2) 通用 ``` ... ``` 围栏
  // 3) substring(firstBrace, lastBrace+1)
}
```

- 没有用 LLM tool calling / structured output。
- 模型一旦在末尾追加解释，substring 抽到的可能是嵌套对象拼接出来的非法 JSON。
- `validateAndNormalizeAgentOutput` 里所有 `nodeIds` 校验是基于 LLM 输出本身的 ID，LLM 写错"job-1"→"jobs-1"就直接整批边被过滤。

**问题 19：prompt 中只取 8 个技能 token，信息丢失严重**

```ts
extractSkillKeywords(...).slice(0,8)
```

- `category` 只用一个字符串，没有向量化或岗位族层级。
- 等级用 7 维加权后的整数 1~5，没有把维度传给 Agent。
- 这导致 LLM 实际拿到的输入比规则引擎还少，质量天花板被 prompt 限制死。

### 2.6 前端可视化（中优先级）

**问题 20：G6 用 d3-force 布局但没固定种子**

- 每次 `loadGraph` 重新跑物理仿真，节点跳来跳去，体验差。
- 没有禁用动画或 cache 上次坐标。

**问题 21：UI 信息密度低**

- 节点颜色只区分 target / promotion / transition 三态，未对 `family` 编码（实际数据里 family 数可达 10+）。
- 边颜色只区分 promotion / transition，`skill_migration` 完全没渲染。
- 没有图例（用户不知道蓝色和橙色是什么）。
- 没有路径高亮：选了一条推荐路径，G6 不会高亮对应链路。
- 雷达图只支持"一个岗位 vs 一个学生"，无法多岗位并列。

**问题 22：后端的查询能力前端没用到**

- `careerPathQuerySchema` 支持 `relation_type` 和 `min_score`，但 `fetchCareerPathGraph` 调用方只传 `depth`。
- 前端 `chartTab === 'graph'` 切换时 `g6Graph?.render()` 才被调用，初次进入若直接 watch 切到 radar，graph 实例不会创建，再切回会闪烁。

**问题 23：没有空态/loading skeleton**

```vue
<p v-if="graphResult && graphResult.edges.length === 0" class="muted empty-hint">
  当前没有可用关系边，建议点击"重建图谱快照"后再查看。
</p>
```

但页面上并没有"重建图谱快照"按钮，文案与功能不一致。

---

### 2.7 测试与可观测性（中优先级）

**问题 24：图谱测试覆盖率低**

- 仅 `jobs-intelligence.graph.test.ts` 测了 `buildAutoCareerGraph` 的几个 case，且这是死代码。
- `buildCareerGraphFromManualPortraits` / `generateCareerGraphByAgent` 没有单测。
- service 的 `getCareerPathGraph` 没有 service-level 测试（mock graphRepository）。
- repository.neo4j 仅有针对 PG / Neo4j 的"是否能连"的 smoke 风格测试，没验证 Cypher 正确性。

**问题 25：图谱质量指标缺失**

`computeGraphQuality` 只算了 `coveredJobs` 和 `isolatedNodeRatio`。需要补：

- 路径多样性（同 source 推荐路径的 family 分散度）
- 平均路径长度、最长可达深度
- 关系类型分布占比
- 推荐 score 分布（直方图）
- top-K 召回评测（人工标注金标准 vs 模型输出）

**问题 26：日志/Trace 不闭环**

- `generateCareerGraphByAgent` 有 `traceId`、有 streaming 进度日志（每 500 字符打一次）。
- `buildCareerGraphFromManualPortraits` 没有 traceId、没有耗时分阶段日志。
- 路由层 `/api/v2/career-paths/...` 不打调用记录，无法 observability。

---

### 2.8 安全 / 多租户（中优先级）

**问题 27：图谱生成接口完全开放**

`POST /api/v2/career-paths/generate` 没有任何鉴权、没有限流、没有幂等键。任何人发请求都会触发 `DETACH DELETE` 全表 + 重新写入。

**问题 28：图谱无租户/版本隔离**

- 所有学生共享同一份 `:CareerRoleV2`。学生 A 的画像驱动图谱重建会影响学生 B 的视图。
- 没有 graph_version 维度的存储（即使 service 返回了 `graph_version`，Neo4j 里只存了一份当前图，无法回滚）。

## 三、优化建议（按优先级与投入回报）

### P0（立即处理，1~2 天可落地）

1. **冻结 V1 路径**：把 `/api/v1/career-paths/*` 标记为 deprecated，matching/report 改造成只调用 `jobs-intelligence` service；后续 V1 模块整体下线，腾出维护精力。
2. **删除死代码**：删除 `jobs-intelligence.graph.ts`（buildAutoCareerGraph）和它的单测；保留 manual + agent 两条主链路。
3. **修掉 V2 路径推荐里的 ID-as-title 漏洞**：`buildRouteRecommendations` 直接从 `snapshot.nodes` 取 title/role_key，让 `step.title` 是岗位中文名，下线前端 `formatRouteText` 正则替换。
4. **`syncGraph` 加事务包裹**：`session.executeWrite(tx => { tx.run(delete); tx.run(unwind nodes); tx.run(unwind edges) })`，避免空窗期。
5. **生成接口加鉴权与限流**：至少加 `x-internal-token` 校验 + per-IP 速率限制，避免外部触发删全表。
6. **前端兜底 ID 移到后端**：`PREBUILT_GRAPH_JOB_IDS` 改成后端 `/api/v2/career-paths/featured` 接口返回，便于运维改配。

### P1（1~2 个迭代内规划）

7. **统一节点 ID 与可读名**：节点 schema 加显式 `display_title` 字段；`role_key` 用纯字母数字 slug（如 `frontend-engineer-l2`），`job_id` 仅用于跳转关联，前后端不再依赖正则。
8. **family / level 加 Postgres 维表**：把岗位族枚举与等级范围从代码常量挪到 `v2_job_families` 表，统一约束并允许多语种。
9. **Neo4j 查询参数化**：用 APOC `apoc.path.expandConfig({ relationshipFilter, maxLevel: $depth })` 替换字符串拼接；同时给 `:CareerRoleV2(family)`、`:CareerRoleV2(job_id)`、`:CAREER_PATH_V2(score)` 加索引。
10. **driver 配置补全**：在 `createNeo4jDriver` 里设置 `maxConnectionPoolSize: 20`、`connectionAcquisitionTimeout: 5_000`、`connectionTimeout: 5_000`，并启用 `disableLosslessIntegers: true` 避免 Number 溢出。
11. **错误识别改用 driver 提供的 code**：`error.code === "ServiceUnavailable"` / `error.retriable === true`，而不是正则匹配 message。
12. **路径推荐引入打分模型**：抽出 `ScoringContext { skillWeight, marketDemand, profileGap }`，把 `transition_cost` 从"gap 数量"改成"加权 gap"。技能权重可以离线计算（IDF + 招聘频次）注入 redis/PG。
13. **图谱质量指标 + 评测脚本**：参考 `npm run knowledge:eval` 模式，新增 `npm run graph:eval`，从 `data/evaluation/career-graph.jsonl` 读金标准（10~20 条人工标注的"目标岗位 → 期望路径"），跑 top-3 命中率 / 路径多样性 / 平均 score 偏差。
14. **前端 G6 信息密度提升**：
    - 按 `family` 上色（提供色板，不超过 10 类）；
    - 加图例 + 关系类型 chip（promotion / transition / skill_migration）；
    - 选中路径时高亮节点和边（修改对应 style）；
    - 路径推荐卡片支持点击 → G6 高亮对应链路；
    - 锁定布局：第一次渲染后调用 `graph.stopLayout()`，避免抖动。
15. **暴露后端查询能力**：前端表单加 `relation_type`（select：全部/晋升/换岗/技能迁移）、`min_score`（slider 0~100），调用 `fetchCareerPathGraph` 时透传。

### P2（设计后规划）

16. **图谱多版本存储**：每次 sync 写入 `graph_version` 标签，Cypher 查询时过滤 `graph_version`，老版本保留 N 份用于审计/回滚；接口返回 `graph_version` 让前端可以选择"当前 / 上一稳定版"。
17. **租户级图谱**：未来支持每位学生的"个性化路径子图"，至少按 `student_profile_id` 分区，写入时打上属性，查询时过滤。可以用 Neo4j 的 multi-database 或属性 + index 分区。
18. **Agent 模式分批 + 缓存**：
    - 按 `family` 切分子图，每族独立调用 LLM；
    - 用 `(portraits_hash, model, prompt_version)` 作为 cache key（pgvector / Redis）；
    - 切换到 LLM tool calling，让模型直接产出 `propose_edge(source, target, ...)` 而不是 JSON 文本，去掉 `extractJsonObjectFromText` 的脆弱解析。
19. **LLM 与规则引擎混合**：让 Agent 只判定"边是否成立 + reason 文案"，候选召回仍由规则引擎（Jaccard + 倒排）做。这样既稳又能拿到自然语言解释，token 成本可控。
20. **可观测性**：
    - 把 `traceId` 透传到所有图谱操作日志（构图/写库/查询）；
    - 在 `/healthz` 增加 `neo4j` 子状态；
    - 引入轻量级监控面板：图谱节点数 / 边数 / 各关系比例 / 最近一次 sync 时间。

### P3（长期）

21. **替换 G6 d3-force 为分层布局**：按 `family` 分组 + `level` 纵向分层（dagre / hierarchical），可读性显著提升。
22. **引入冷热分离**：把"高频访问的子图"缓存到 Redis（key=`graph:{job_id}:depth={depth}`），图谱重建时统一失效，让 P95 查询延迟降到 <50ms。
23. **接入岗位实时供需信号**：从招聘 RSS / 问卷数据抽取"近 30 天热度"，作为 edge `score` 的动态调整因子，每日定时刷新一次。

## 五、结论

当前图谱功能**已经能跑通完整链路**：从 `v2_manual_job_portraits` 到 Neo4j 再到 G6 可视化，前端展示也具备基础观感。但**架构层（V1/V2 双轨）、算法层（魔数评分 + 等权技能）、可观测层（缺评测/索引/日志）** 的债务都很重，长远扩展会被这些点绊住。

短期内最值得做的三件事是：

1. **下线 V1**，让所有图谱走 V2 一条链路；
2. **修掉路径推荐 ID-as-title 这个明显数据契约缺陷**，停止依赖前端正则补漏；
3. **建立图谱评测脚本与质量指标**，让"超参调整"和"算法替换"有客观依据，否则后续接 LLM / 上线供需信号都没法量化收益。

完成 P0 之后再分批推进 P1（性能、可视化、可观测）和 P2（多版本/多租户/Agent 改造），整体落地周期约 4~6 周。
