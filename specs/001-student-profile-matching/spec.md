# Feature Specification: 学生画像与人岗匹配评分

**Feature Branch**: `001-student-profile-matching`  
**Created**: 2026-04-02  
**Status**: Draft  
**Input**: User description: "为 Career Agent 新增学生画像 + 人岗匹配四维评分 + 匹配结果解释能力，支持简历上传/手动录入、岗位选择、匹配查询与详情，接口需明确请求/响应/错误结构，结果可复现并可用于后续报告生成"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 生成学生画像并完成单岗位匹配 (Priority: P1)

大学生提交简历文件或手动填写经历后，系统生成可读的学生能力画像；
学生选择一个目标岗位后，系统返回四维评分、总分、差距项和改进建议。

**Why this priority**: 这是最核心的业务闭环入口，若该能力不可用，则后续查询、报告、运营评估均无法成立。

**Independent Test**: 使用一份有效简历样本与一个存在的岗位，独立验证“提交输入 -> 画像生成 -> 匹配评分 -> 结果展示”全流程可完成。

**Acceptance Scenarios**:

1. **Given** 学生已提供合法简历文件且目标岗位存在，**When** 学生发起匹配分析，**Then** 系统返回四维得分、总分、差距项和建议，并包含可追溯的结果标识。
2. **Given** 学生选择手动录入并填写完整必填信息，**When** 学生发起匹配分析，**Then** 系统生成与简历上传入口等价的学生画像并完成同样的评分输出。

---

### User Story 2 - 查询匹配结果列表与详情 (Priority: P2)

学生可按本人画像或目标岗位查询历史匹配结果列表，并进入单条详情查看评分构成、差距解释与建议内容。

**Why this priority**: 匹配结果必须可回看、可比较，才能支持持续优化职业规划与后续报告使用。

**Independent Test**: 预置多条匹配记录后，验证列表筛选、分页与详情查看可独立完成，且数据与创建时一致。

**Acceptance Scenarios**:

1. **Given** 系统中存在多条匹配结果，**When** 学生按目标岗位或时间范围查询，**Then** 系统返回符合条件的结果列表并可进入任一详情页查看完整解释信息。
2. **Given** 学生打开某条匹配详情，**When** 该结果存在，**Then** 系统返回与创建时一致的四维分值、总分、差距项与建议文本。

---

### User Story 3 - 匹配结果可复现并可被报告模块复用 (Priority: P3)

相同输入在相同岗位下重复计算时，系统输出一致结果；同时匹配结果可被报告模块读取，作为报告生成依据。

**Why this priority**: 复现性是可信度基础，报告复用是后续能力扩展前提。

**Independent Test**: 对同一学生画像和同一岗位重复提交匹配请求，验证输出一致；再验证报告模块可通过结果标识读取匹配结论。

**Acceptance Scenarios**:

1. **Given** 学生画像数据与岗位画像数据均未变化，**When** 在同一规则版本下重复发起匹配，**Then** 返回的四维分值、总分与差距项保持一致。
2. **Given** 匹配结果已落库，**When** 报告模块按结果标识读取，**Then** 可获得完整且结构化的匹配结论数据。

---

### Edge Cases

- 简历文件格式合法但内容为空或无法提取有效信息时，系统如何返回可理解的失败原因与修复建议。
- 学生手动录入缺少必填字段时，系统如何返回字段级错误并阻止进入评分。
- 目标岗位不存在、已下线或不可匹配时，系统如何返回明确错误并提示用户重新选择。
- 匹配计算过程中出现内部异常时，系统如何返回标准化 5xx 错误且不泄露内部实现细节。
- 已存在同输入的匹配结果时，系统如何避免产生语义重复且不一致的数据。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持两种学生输入方式：简历上传与手动录入。
- **FR-002**: 系统 MUST 基于学生输入生成结构化学生能力画像，并可被后续匹配流程直接引用。
- **FR-003**: 用户 MUST 能从岗位列表中选择单个目标岗位发起匹配分析。
- **FR-004**: 系统 MUST 输出四维评分（基础要求、职业技能、职业素养、发展潜力）及总分。
- **FR-005**: 系统 MUST 输出差距项解释与可执行改进建议，且建议需与低分维度对应。
- **FR-006**: 系统 MUST 保存每次匹配结果，并支持按学生、岗位、时间进行查询。
- **FR-007**: 系统 MUST 提供匹配结果详情查询，返回评分明细、差距项与建议全文。
- **FR-008**: 在输入数据与规则版本不变时，系统 MUST 保证匹配结果可复现（同输入同输出）。
- **FR-009**: 匹配结果数据 MUST 可被报告模块以稳定标识读取。
- **FR-010**: 系统 MUST 在请求参数缺失、格式非法、资源不存在时返回可区分的客户端错误。
- **FR-011**: 系统 MUST 在内部处理失败时返回标准化服务端错误，并提供可追踪信息。
- **FR-012**: 系统 MUST 明确本需求范围边界，不包含复杂图谱可视化与外部招聘平台对接。

### API Contract Requirements *(mandatory when API is involved)*

- **AC-001**: MUST 明确每个接口的 Path/Query/Header/Body 参数，包含字段名、类型、是否必填、约束与示例。
- **AC-002**: MUST 明确成功响应结构，包含状态码、字段定义、示例。
- **AC-003**: MUST 明确错误响应结构，至少区分 4xx 与 5xx，包含错误码/错误信息/可选追踪字段。
- **AC-004**: MUST 在 `packages/contracts/openapi` 与 `packages/contracts/types` 完成变更后，
  再进入后端和前端实现。
- **AC-005**: MUST 为“创建画像”“发起匹配”“查询列表”“查询详情”定义一致的错误语义，
  并保证前端可据此稳定渲染。

### Implementation Constraints *(mandatory)*

- **IC-001**: 变更 MUST 保持 Monorepo 结构，不拆分仓库。
- **IC-002**: 前端代码 MUST 放在 `apps/frontend` 并遵循 `app/features/shared` 分层。
- **IC-003**: 后端代码 MUST 放在 `apps/backend` 并遵循
  `route/schemas/service/repository/repository.adapter` 分层。
- **IC-004**: `service` 层 MUST 通过 `repository` 抽象访问数据，不直接依赖具体存储。
- **IC-005**: 实现 MUST 使用 TypeScript，关键逻辑需补充高质量中文注释。

### Key Entities *(include if feature involves data)*

- **StudentProfile**: 学生能力画像，包含基础信息、经历摘要、能力维度、画像版本、生成时间。
- **JobProfile**: 目标岗位画像，包含岗位要求维度、权重配置、岗位版本信息。
- **MatchResult**: 一次学生画像与岗位画像的匹配记录，包含四维分值、总分、差距项、建议、规则版本与结果标识。
- **MatchExplanationItem**: 匹配解释条目，描述某一维度的证据、缺口与建议动作。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 90% 以上的目标用户可在 5 分钟内完成“输入资料 -> 选择岗位 -> 查看匹配详情”的完整流程。
- **SC-002**: 在验收样本集中，100% 匹配结果均包含四维评分、总分、至少 1 条差距项与至少 1 条改进建议。
- **SC-003**: 对同一输入和同一岗位重复执行 20 次，结果一致率达到 100%。
- **SC-004**: 95% 以上的匹配结果详情请求可在 2 秒内返回给用户。
- **SC-005**: `npm run type-check` 在本需求交付分支上 MUST 通过。

## Assumptions

- 目标用户为需要进行职业规划的在校大学生或应届毕业生。
- 岗位画像数据在本需求实施时已可用，并可稳定支持岗位列表选择。
- 简历上传支持的文件类型与大小限制遵循当前平台统一上传规范。
- 本需求聚焦单学生与单岗位匹配，不包含多岗位批量对比和复杂图谱分析。
- 报告模块在本阶段只消费匹配结果，不要求同时改造报告生成策略。
